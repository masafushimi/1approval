1Approval 管理機能 追加分 画面仕様

2026-09-22
この文書は既存の仕様レビューとは切り分けてあります。あちらは機能①〜⑬のレビューと確定事項をまとめたもので、そのまま有効です。こちらは新しい機能案（購買の入口を増やす一連の提案）を採用した場合に、追加・改修が必要になる管理画面だけを書いたものです。採用しない場合、この文書は丸ごと不要になります。
目次この文書の範囲最大の構造変化 — 取引先が主要オブジェクトになる新規画面消耗品の消費ペースをどう測るか既存画面の改修メニュー構成への影響フェーズの切り分け先に決めること

この文書の範囲

前提となるのは、購買を1Approvalに取り込む入口を5つに増やすという提案と、それに付随する2つの仕組みです。

前提の機能内容
EC連携（PunchOut）既存。モノタロウなど対応済みのEC
見積依頼フォーム会社名・メールアドレス・品名・数量の4項目で見積依頼を送る。EC以外の仕入先が対象
Chrome拡張PunchOut連携していないECサイトから、商品情報を拾って申請を立てる
見積の受信サプライヤーから届いた見積を専用アドレスに転送すると、申請の下書きが立つ
スケジュール起票SES・保守・定期契約などを、期日で自動起票する
ワンタイムカード承認と同時に使い切りカードを発行し、承認金額を支払の上限として執行する
取引先の主格化下記のとおり、取引先が購買の起点になる

これらを実装すると、新規20〜25画面、既存7画面の改修が発生します。既存仕様の73画面に対して、おおよそ95画面前後になる規模感です。

最大の構造変化 — 取引先が主要オブジェクトになる

既存仕様で取引先は、会計連携の項目マッピングの一部として扱われています。部門マスタや勘定科目マスタと並ぶ、設定の中の1項目です。

新機能を入れると、取引先は購買の起点そのものになります。

  • 見積依頼の宛先になる
  • 新規かどうかで事前承認の要否が決まる
  • 法人番号・T番号・ドメインで実在を確認する
  • 取引先ごとに購買カタログが育つ（過去品目と価格履歴）
  • 受信した見積メールの送信元照合に使う
  • スケジュール起票の宛先になる

設定の中に置くには重すぎるので、メニューに独立した群が必要になります。

もう一段の変化 — 誰がマスタを作るのか

既存仕様は「初期データ移行」画面で既存マスタを取り込む前提です。しかし新機能では、申請時に現場が打った会社名から取引先が自動で生えます。

つまり取引先マスタが、管理者が整備するものから、使ううちに育つものへ変わります。購買カタログと同じ構造で、同じ問題を抱えます——表記揺れで同じ会社が複数生まれる。だから法人番号を主キーにする設計と、名寄せ・統合画面がセットで要ります。ここを後回しにすると、半年後にマスタが壊れます。

消耗品の消費ペースをどう測るか

スケジュール起票のトリガーのひとつに在庫があります（既存仕様の自動購買申請もここに統合されます）。しかしこの方式は理論在庫が正しいことを前提にしています。理論在庫は検収で増えて出庫で減る値なので、検収と出庫の記録が始まる Phase-1 以降でなければ存在しません。

一方、消費ペースの推定には購買履歴だけで足りる方法があります。こちらは Phase-0 で成立します。

3つの測り方

方式消費ペースの出所消費と紛失現場の手間成立時期
継続記録法出庫を都度記録分離できる出庫のたびにスキャンPhase-1〜
棚卸計算法期首＋入庫−期末分離できない棚卸しのときだけPhase-1〜
購買間隔法購買履歴から推定分離できないなしPhase-0〜
購買間隔法を既定に推奨します。Phase-0 は「他システムで買ったものを集めて見せるだけで、発注も検収もしない」フェーズですが、購買履歴だけは最初からあります。つまり現物管理（QR貼付・初期棚卸）をまったく始めていない段階でも、買い足しどきの提案が出せます。Phase-0 の導入負担を増やさずに機能を1つ増やせる、という点でかなり大きい。

軍手やボルトのような低単価のバラ物について、出庫をいちいち記録させる運用は続きません。機能群の切り分けでも「高額品と期限管理品だけ先に入れ、消耗品は運用開始後の購買から自然に溜める」方針を採っており、購買間隔法はこれと整合します。

推定の仕方

n 回目の購買で得られるサンプルは、前回買った量を、次に買うまでの日数で割った値です。

消費率ᵢ ＝ 数量ᵢ₋₁ ÷ ( 発注日ᵢ − 発注日ᵢ₋₁ )

間隔だけを見てはいけません。まとめ買いした回で「消費が減った」と誤読します。

  • 平滑化は EWMA（指数加重移動平均）。単純移動平均は窓幅を決める必要がありますが、購買頻度は品目ごとに大きく違うので、固定窓は必ずどれかで外れます。EWMA ならパラメータは α ひとつです
  • 外れ値の除去は必須。価格改定前の駆け込みまとめ買いが1回混ざるだけで、単純平均は数か月壊れます
  • 粒度は拠点・部署ごと。全社平均は誰の実態でもない数字になります
  • 閾値の単位が変わる。実在庫を知らないので「残り◯個で起票」は指定できません。「残り◯日分で起票」になります

効かなくなる3つのケース

ケース何が起きるか
欠品していた期間がある切らして我慢していた分は購買に現れない。実消費を過小評価する
他拠点から融通した買わずに済んだので間隔が伸びる。同じく過小評価
システム起票が学習データに混ざる下記。設計上いちばん厄介

自己成就を避ける

システムが予測日に起票し、承認されて発注されると、その発注間隔がそのまま次の学習データになります。放置すると推定値が自分の予測を学習し続け、実態から乖離しても誰も気づきません。

対策として、起票履歴に起点（システム／人）のフラグを持たせます。人起点の実績を重く見るか、定期的に人起点の実績だけで検算します。起票履歴画面はもともとスキップ理由を残す設計なので、同じ場所に起点も残せます。

棚卸しの位置づけが変わる

消費ペースの主たる出所が購買履歴になるため、棚卸しは較正点になります。年1回の実測で、推定から積み上げた理論値とのズレを見て推定をリセットする。ズレの大きい品目は、融通や紛失が起きている品目として炙り出せます。

既存仕様の「棚卸の差異は理由を選んでから確定する。自動上書きは差異の原因が追えなくなるため非推奨」という方針は、そのまま有効です。差異を消費として自動計上してはいけません。

画面への影響

画面何が変わるか

/schedules/history 起票履歴起点の列（システム／人）。自己成就の検算に使う
/partners/:id/catalog 購買カタログ品目ごとの消費ペースと次回予測日。ただし下記の論点あり

監査ログについて

既存仕様は監査ログを「会計数値の変更を追う」目的で置いています。新機能ではこれに「金が動く根拠を追う」目的が加わります。この2つは要件が違います。

とくに、みなし検収について既存仕様は「監査で誰が検収したのかを聞かれたときに、人ではなくルールだと説明できる必要がある」と書いていますが、送金の文脈では「ルールです」は説明になりません。そのルールを設定した人の判断責任になるので、リードタイムや自動検収の上限金額を変更した履歴が、通常の設定変更ログより重い意味を持ちます。

メニュー構成への影響

既存仕様のメニューは5群です——購買（台帳・支出分析）、モノ（検収・備品・在庫・期限・貸出・棚卸・リース）、IT・SaaS、人（メンバー・入退社）、設定。

群変化
購買厚くなる。台帳・支出分析に加えて、見積依頼・入口別分析
取引先（新設）一覧・詳細・カタログ・名寄せ・未確認キュー。設定から独立させる
モノ変化なし
IT・SaaS / 人変化なし
設定メール、拡張、スケジュール、カードが加わる

カード関連は、設定（発行ルール）と運用（発行済み一覧・照合）で置き場所が分かれます。運用側は購買群に置くのが自然です。

フェーズの切り分け

全部を同時に作る必要はありません。実装の順番はメール基盤（見積の受信＋見積依頼）が1番目を推奨しています。同じ土台なので分けて作る意味が薄く、受信のほうが導入の摩擦が低いためです。

Phase-0 に要るもの

  • 取引先マスタ（法人番号・T番号・ドメイン）— 外部データ標準のセマンティクス層と同じ話なので、どのみち作る
  • 見積依頼の一覧・詳細
  • 見積回答の確認・確定
  • メール設定と受信の振り分け
  • ルール設定の拡張
  • 消費ペースの推定 — 購買履歴だけで成立するため、現物管理を始める前から使える。詳細

後でよいもの

  • 取引先の名寄せ・統合 — データが溜まってから。ただし法人番号を主キーにする設計だけは最初から
  • 購買カタログ — 2回目以降の申請が発生してから
  • 拡張・カード・スケジュールの管理画面 — それぞれの機能を作るとき
  • 入口別分析 — 入口が複数になってから

先に決めること

  1. 取引先マスタを誰が作るのか。管理者が整備するのか、申請から自動で生えるのか。後者なら名寄せ・統合が必須になる
  2. 取引先を独立したメニュー群にするか。設定の中に置き続けると、カタログと名寄せの置き場所が苦しくなる
  3. 監査ログの対象範囲。カード発行とスケジュールルールの変更を追跡対象に含めるか
  4. 画面数の増加を許容するか。73画面 → 95前後。ワイヤーフレームの作り直しコストが発生する
  5. 消費ペースを購買履歴から推定するか。採用すれば Phase-0 の段階で買い足しの提案が出せる。ただし品目マスタの名寄せが必要になる
