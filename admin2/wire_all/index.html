追加分の画面一覧とフェーズ構成

2026-09-21
この文書は既存の画面一覧とフェーズとは別建てです。あちらは73画面の構成で、そのまま有効です。ここに書くのは、購買の入口を増やす提案を採用した場合に追加される22画面と、既存7画面の改修だけです。採用しない場合はこの文書ごと不要になります。
目次入口が増えても台帳は1本フェーズ構成追加される22画面既存画面の改修URL の規則作っていないもの

入口が増えても台帳は1本

追加される画面の大半は入口を増やすためのものです。入口が何本あっても、出てくるものは同じ「発注」なので、台帳から先は既存の73画面がそのまま使えます。

flowchart LR A1[EC連携<br/>PunchOut] --> N{内部の文書型} A2[見積依頼<br/>フォーム] --> N A3[Chrome拡張] --> N A4[見積の受信<br/>転送] --> N A5[スケジュール<br/>起票] --> N N --> B[購買明細台帳] B --> C[承認・発注] C --> D[検収] D --> E[在庫・資産・会計]

だから入口が増えるたびに触るのはアダプタだけで、承認も台帳も検収も会計出力も入口を区別しません。これは既存仕様の文書モデル層を採る前提で成り立ちます。

フェーズ構成

22画面を3段階に分けます。メール基盤（見積の受信＋見積依頼）が1番目です。同じ土台なので分けて作る意味が薄く、受信のほうが導入の摩擦が低いためです。

フェーズ枚数ねらい画面
Phase-010画面取引先と見積依頼、そのメール基盤。ここまでで EC以外の仕入先が制度に乗る取引先一覧、取引先詳細、名寄せ・統合、未確認キュー、見積依頼一覧、見積依頼詳細、見積回答の確認・確定、依頼メールのテンプレート、メール設定、受信の振り分け
Phase-16画面カタログ、Chrome拡張、ワンタイムカード。立替と購入報告がここで消える購買カタログ、対応サイト管理、取得成功率モニタ、カード発行ルール、発行済みカード、決済の照合
Phase-26画面自動起票と分析。入口が揃ってから効いてくるスケジュール起票 ルール一覧、ルール編集、起票予定カレンダー、起票履歴、入口別の支出、カバレッジ

URL の規則

既存の規則をそのまま踏襲します。運用する画面はルート直下、設定は /settings/ 配下。

接頭辞置くもの例
/partners/取引先。新設の群/partners/:id/catalog
/quotes/見積依頼。運用画面/quotes/:id/review
/mail/受信の振り分け/mail/inbox
/cards/発行済みカードと照合/cards/reconciliation
/schedules/起票の予定と履歴/schedules/calendar
/settings/ルールと接続/settings/extension/health
/purchases/analytics/分析。既存の購買群にぶら下げる/purchases/analytics/coverage

作っていないもの

  • モバイル画面。検収・出庫・棚卸は既存の73画面にあり、今回の追加分で現場がスマホを使う場面は少ない。ただし承認は別で、リードタイムが定着を左右するので、既存のモバイル承認を前提にしています
  • Chrome拡張そのもののUI。ブラウザ側で動くので管理画面ではありません。対応サイト管理と取得モニタだけが管理画面側です
  • サプライヤー向けポータル。サプライヤーに登録を求めないのがこの提案の骨子なので、作りません
  • 1Approvalが買い手になる場合の画面（まとめ請求・与信・債権管理）。事業モデルの判断が先で、決まってから設計します
