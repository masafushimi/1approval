追加分の機能群の切り分けとプライシング

2026-09-21
既存の機能群の切り分けは、基本＋7オプションの構成です。ここでは、購買の入口を増やす提案を採用した場合に、その22画面をどこに乗せるかだけを書きます。既存の値付けには手を入れません。
目次結論切り分けの原則機能群ごとの中身見積例値付けの根拠とリスク

結論

取引先は Core に入れ、入口は3つのオプションに分ける。取引先まわりは他のすべての土台なので切り出せません。入口はそれぞれ独立して価値が出るので、別売りにできます。

機能群枚数位置づけ価格の考え方
取引先5画面Core に統合値上げなし。既存Coreの前提を強くするもの
見積依頼（メール基盤込み）6画面新オプション月額固定。テールスペンドの本丸
Chrome拡張2画面＋拡張本体新オプションユーザー課金。使う人の数に比例する
ワンタイムカード3画面新オプション月額固定＋決済件数。カード事業者への支払いが原価
自動起票4画面Core に統合値上げなし。既存の自動購買申請を統一するもの
分析2画面Core に統合値上げなし。効果測定そのものなので外すと売れない

切り分けの原則

既存の原則をそのまま使います。単独で価値が完結するものだけをオプションにする。そのうえで、今回は3つ足しました。

  1. 土台はオプションにしない。取引先マスタと自動起票は、他の機能が乗る前提になるので Core。取引先を外すと見積依頼もカタログも受信も成立しません
  2. 効果測定は売らない。分析（入口別・カバレッジ）は、オプションを買ってもらうための根拠そのもの。「導入したが効果が見えない」を防ぐために Core に入れます
  3. 原価が変動するものは従量を混ぜる。ワンタイムカードはカード事業者への支払いが発生するので、固定だけにしません

機能群ごとの中身

Core に統合（値上げなし）

取引先5画面、自動起票4画面、分析2画面の計11画面。

取引先が Core に入ると、既存Coreの会計連携の精度が上がります。法人番号を主キーにするので、6製品への出力で最も失敗する取引先名の表記揺れが構造的に消える。つまりこれは新機能というより、既存機能の品質改善として売れます。

自動起票も同じです。既存仕様には時間トリガーの自動起票が3か所バラバラにあるので、統一するだけなら新しい価値ではなく整理です。

見積依頼 — 新オプション（6画面）

見積依頼4画面＋メール基盤2画面。これが一番大きいと思います。

訴求は「EC以外の仕入先が制度に乗る」こと。効果は立替精算の件数と、1Approvalを通った購買の割合に出ます。見積の受信だけ先に使ってもらう形にすると、導入の摩擦がさらに下がります（頼み方は今のままで、転送するだけ）。

値付けの注意。メール基盤は送信数に比例して原価がかかります（到達率を保つための送信基盤）。中堅企業の見積依頼は月に数十〜数百件規模なので固定で吸収できますが、上限は決めておくべきです。

Chrome拡張 — 新オプション（2画面＋拡張本体）

対応サイト管理と取得モニタ。ユーザー課金が向いています。拡張を入れた人しか使わないので、全社課金にすると割高に見えます。

ただし保守コストが恒久的にかかります。個別対応したサイトはEC側の画面変更で壊れるので、対応サイト数に上限を設けるか、上位プランで対応サイトを増やす形にします。

ワンタイムカード — 新オプション（3画面）

発行ルール、発行済み一覧、決済照合。訴求は立替解消ではなく統制です。承認そのものが支払の上限として執行されるので、内部統制の文脈で値段がつきます。

前提として、顧客がバーチャルカードの都度発行に対応した法人カードを使っている必要があります。自前で発行すると与信と資金決済法の論点を呼び込むので、そこには踏み込まない前提です。

見積例

従業員300名・拠点3・EC以外の仕入先が多い製造業を想定します。

構成内容
Core購買明細台帳、分類、会計出力＋取引先・自動起票・分析
＋ 見積依頼EC以外の仕入先を取り込む。本丸
＋ ワンタイムカード立替精算をゼロにし、承認を支払の上限として執行する
（拡張は見送り）情シスが拡張のインストールを許可しないため。先に主要ECの正規連携を調べる

拡張を外すという判断が普通にありえます。だから入口ごとに独立して売れる形にしておくことが重要です。

値付けの根拠とリスク

根拠になる数字

顧客に示せるのは、既存Coreと同じく削減できる作業量です。

  • 立替精算の件数と金額。これは導入前後で直接比較できる
  • 取引先登録の事務。1社あたりの登録工数 × 新規取引先数
  • 見積取得の代行。購買部が現場の代わりに見積を取っていた工数
  • 突合作業。支出が最初から台帳に乗るので、請求書と発注の突合が減る

リスク

  • 定着しないと数字が出ない。現場にとって「記録に残る」は価値ではなくコストなので、通したほうが速くなければ元のやり方に戻ります。リードタイムが悪ければ、機能として正しくても失敗します
  • 拡張の保守が読めない。EC側の画面変更は相手の都合なので、こちらで制御できません。対応サイト数に上限を設けないと原価が青天井になります
  • カードは顧客の環境に依存する。対応した法人カードを使っていない顧客には売れません。請求書払いのみのBtoB ECも残るので、支払手段は複数持つ前提です
  • 取引先を Core に入れると、値上げの機会を1つ失います。ただし切り出すと他のオプションが全部成立しなくなるので、ここは飲む判断です
