このドキュメントについて

1Approval の画面仕様を、73枚のワイヤーフレームから起こしたものです。画面ごとに、何を決める画面か・何を表示するか・どの操作が何を起こすかを書いています。

対象は 1Approval for Goods（備品・消耗品の購買と資産管理）の管理画面を中心に、そこから派生する5つのフェーズです。出張手配は Phase-3 のエージェントとして扱い、それ以外の 1Approval for Trip 固有機能は対象外です。

粒度は「実装者が画面を組める」ところまでです。データモデルと状態遷移は、仕様レビューに分けてあります。

フェーズ構成

6フェーズ・合計73画面。Phase-1 だけで40画面で、ここが製品の本体です。

フェーズ内容解く問題画面数
Phase-1購買・検収・分類・モノの管理・設定承認＝発注を成立させ、届いたあとの台帳を自動で埋める40
Phase-2固定資産ソフト・MDM・SaaSライセンス買ったものと、外部システムが持つ台帳のずれを消す3
Phase-31Approval Agent Purchase申請者がカタログを探さなくても済むようにする6
Phase-4人事・組織マスターの一括同期入退社で備品とライセンスが取り残されるのを止める2
Phase-5社内規程のRAG学習・全社標準品カタログ「何を買ってよいか」を規程と標準品から決める2
Phase-61Approval Ads（B2B広告事業）購買先メーカーからの収益を作る4

順番には理由があります。Phase-3 の AI レコメンドは、Phase-1 で貯まった購買明細（品番・数量・周期・納入先）がないと提案できません。Phase-5 の標準品カタログは、申請画面（Phase-3）がないと効かせる先がありません。Phase-6 は掲載面が Phase-3 なので、その後になります。

3つのシステム

73画面は、1つの製品ではなく、使う人が違う3つのシステムに分かれます。見た目を意図的に変えています。

Ads の4枚のうち、掲載イメージは Agent Purchase の中（app/agent）、受け入れ設定は管理画面の中（/settings/ads）にあります。

モノ：個体管理（8枚）

備品・資産（/assets）、個体詳細（/assets/:id）、QRラベル（/assets/labels）、ラベルのプレビュー（/assets/labels/preview）、点検・修理（/assets/maintenance）、点検記録の登録（/assets/maintenance/new）、廃棄・除却（/assets/disposals）、除却の起票（/assets/disposals/new）。

モノ：数量と貸出（9枚）

在庫（/stock）、拠点間の移動（/stock/transfers）、移動の起票（/stock/transfers/new）、期限（/expiry）、貸出（/loans）、貸出カレンダー（/loans/calendar）、貸し出す・返す（/loans/new）、SP 出庫（/m/issue）、SP 貸出（/m/loans）。

貸出カレンダーは個体 × 2週間のガント。稼働率8割超は台数不足、1割未満は見直し候補として提示します。

棚卸とリース（6枚）

棚卸（/stocktakes）、棚卸の起票（/stocktakes/new）、差異確定（/stocktakes/:id/diff）、リース契約（/leases）、リース契約の登録（/leases/new）、SP 棚卸（/m/stocktakes）。

棚卸の差異は「理由を選んでから確定」が既定です。自動上書きは差異の原因が追えなくなるため非推奨。

人（3枚）

メンバー（/members）、メンバーの詳細（/members/:id）、入退社（/members/onboarding）。

メンバーの詳細で、1人の持ち物・SaaS・購買傾向が1枚に集まります。退職時に何が残るかがここで分かります。

設定（11枚）

購買設定（/settings/purchasing）、品目の編集（/settings/purchasing/items/:id）、ルール設定（/settings/rules）、システム設定（/settings/systems）、kintone接続（/settings/systems/kintone）、購買先の接続（/settings/systems/:ec）、接続を追加（/settings/systems/new）、接続テスト（/settings/systems/:ec/test）、勘定奉行（/settings/systems/obc）、楽楽精算（/settings/systems/rakuraku）、接続ログ（/settings/systems/logs）。

品目の編集に登録した品目は、分類の確定を通らず自動確定します。購買先の接続では「誰が使えるか（拠点・部署・ロール）」と「カタログの範囲」を決めます。接続している購買先が、そのまま会社が認めた購買先です。

権限・拠点・記録（4枚）

権限とロール（/settings/roles）、ロールの編集（/settings/roles/:id）、拠点とロケーション（/settings/locations/:id）、監査ログ（/settings/audit）。

ここで決めるのは 1Approval の画面で何ができるかです。購買の承認権限は kintone / M365 側で決まります。

このほかに、ホーム（/）、通知（/notifications）、通知設定（/settings/notifications、16種類 × 4経路）、ログイン（/login）、初期データの移行（/settings/import）があります。

画面の関係と URL の規則

一覧は複数形、詳細は ID、新規作成は /new で統一しています。

flowchart LR A[購買明細台帳<br/>/purchases] --> B[分類の確定<br/>/classify] A --> C[検収<br/>/receiving] C --> D[差異の処理<br/>/discrepancy] A --> E[支出分析<br/>/analytics] E --> F[予算設定<br/>/budgets] C --> G[在庫・資産台帳] B --> H[会計・経費へ出力]

台帳から始まって、検収でモノの管理に分岐し、分類の確定で会計に抜けます。この3本が Phase-1 の背骨です。

導線の規則は4つです。

  1. 操作ボタンの宛先は一覧ではなく起票画面。「貸し出す」は /loans ではなく /loans/new へ
  2. どの画面にも下部に「つながる画面」を置き、前の画面・次の画面・関連を並べる
  3. CSV出力は遷移ではなくその場のダウンロード
  4. 完了のフィードバックはポップアップで、取り消せる条件を必ず書く

Phase-1〜2 は 1approval.app、Phase-3 は app.1approval.com、Phase-6 の広告主向けは ads.1approval.com です。スマホは /m/ 配下にまとめ、QR からは /a/:id で個体詳細に飛びます。

作っていないものと、主な設計判断

意図的に作っていない画面があります。

  • kintone / Microsoft 365 上の承認カード。各基盤のUIで作るもので、この管理画面の対象外です。管理画面側に必要なのは、承認カードに何を出すかのマッピング設定だけです
  • カード明細・交通系IC・立替精算。経費精算と Trip の領域です。ただし購買明細台帳のデータ構造は、後からチャネルを足せる形にしておきます
  • RFP・相見積の比較。単発高額品の業務で、消耗品の購買統制とは別物です

仕様を読むときに知っておくべき判断が4つあります。

発注は原則として止めません。 ルールに引っかかっても記録して承認者に判断させます。止めると現場が台帳の外で買い、見えなくなるからです。

受け取っていない数量は台帳に載せません。 検収した数だけが在庫になります。だから数量差異で除却は発生しません。除却は受け入れた後に壊れた・期限切れだと分かったときだけです。

減額方向は再承認不要、増額方向は再承認。 事前承認は「この金額まで使ってよい」という枠なので、枠内なら通し、超えるなら戻します。

広告を受け入れても利用料は下がりません。 値引きを条件にすると断れなくなり、購買統制ツールが広告に買われていると見られた時点で製品の信頼が崩れます。
