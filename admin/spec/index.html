1Approval 管理機能 仕様レビュー

2026-09-20
目次決定事項全体設計の前提分類エンジン（機能②③④を一本化）購買明細台帳と検収現物管理（機能⑤〜⑧）人と外部台帳、承認基盤連携仕様から抜けていた機能データモデルと状態遷移外部データ標準（Peppol / EN16931）モノタロウ接続アストロラボとの突合UI 設計実装順序と、残る論点

機能①〜⑩のレビューと、その後に確定した決定事項・外部仕様・UI設計を、時系列ではなく実装の順番で並べ直したものです。

最重要の提言は2つです。機能②③④を別々に作らず、一つの分類エンジンの3つのビューにすること。そして検収画面を最初に作ること。検収が在庫・資産・期限のすべての起点です。

決定事項

要決定11件はすべて回答済みです。実装の前提としてここを見てください。

論点決定仕様への影響
消耗品の出庫QRでの出庫を基本とし、定期棚卸の差分と購買サイクルから消耗サイクルを検知リアルタイム在庫を持つ。管理するものとしないものを品目マスタで分ける
固定資産のしきい値テナント（顧客企業）ごとに設定10万／20万／30万を固定値にしない。中小企業特例の適用有無もテナント設定
税情報明細行ごとに詳細に持つ税率区分・税抜金額・税額を分けて保持。仕訳CSVの精度が上がる
電帳法スコープに入れる取引年月日・金額（範囲）・取引先で検索できること。ダウンロードした証憑の保存も含む
マルチテナント行レベル分離（PostgreSQL RLS）全クエリにテナントとスコープが効くこと
個体ID既存の資産番号体系を引き継ぐ移行時に重複と欠番を検出。新規分だけ 1Approval の規則で採番
QRラベルPDF一括印刷A4面付け、開始位置のずらし、耐候ラベルの選択
自動購買申請申請の自動作成まで発注はしない。同一SKUで未完了の申請がある間は再起票しない

外部データ標準EN16931 / JP PINT のセマンティクスを内部の正規化モデルに採用する。外部との入出力は4文書型に正規化する。Peppol ネットワークへの接続そのものは条件付きで先送り税区分・単位・取引先の識別子を規格のコード体系で持つ。EC接続は「外部フォーマット → 内部4文書」の変換アダプタになる

このうち実装に最も重く効くのはリアルタイム在庫です。在庫を持つと決めた以上、出庫の瞬間を定義する必要があり、それがQR出庫です。ただし紙や付箋まで追うのは無理なので、管理対象外という区分を品目マスタに持たせます。

全体設計の前提

個別機能より先にこの6つを決めてください。あとから直すのが高いものばかりです。

1. 3層構造にする

購買明細が1本あり、そこから分類されて各台帳に分かれる、という流れです。

flowchart TD A[購買明細<br/>PurchaseLine] --> B{分類エンジン} B -->|固定資産| C[個体台帳<br/>AssetItem] B -->|消耗品| D[在庫<br/>StockBalance] B -->|管理対象外| E[台帳に載せない] C --> F[貸出・点検・除却] D --> G[出庫・棚卸] C --> H[期限管理] D --> H

消耗品と期限管理は排他ではありません。試薬は消耗品であり、同時に期限管理対象です。この事実が分類エンジン一本化の根拠になります。

2. ID体系を先に決める

品目を指すIDと、現物を1点ずつ指すIDを分けます。SKUの名寄せは必須で、同じ手袋が購買先ごとに違う品番で来ます。JAN と自社品目コードの両方を持ち、どちらかで突合します。仕入先品番も第3の系統として持ちます。

あわせて取引先IDと単位コードも、ここで規格に寄せます。取引先は法人番号（Peppol の参加者識別スキーム 0188 が採る体系）を主キーにし、T番号は別項目にします。単位は UN/ECE Rec.20 のコードと自社表記の両方を持ちます。「箱」「ケース」「入」の表記揺れを正規化しないと、安全在庫の式（平均消費量 × リードタイム）が単位混在で壊れます。詳細は外部データ標準の章に置きました。

個体IDは既存体系を引き継ぐと決まったので、採番規則はテナントごとの設定になります。拠点接頭辞＋種別＋連番が既定値です。

3. 権限は行レベルで持つ

ロールだけでは足りません。スコープ（拠点・部門）を全クエリに効かせます。ただし例外が1つあり、他拠点の在庫数だけはどのロールでも見えるようにします。見えないと重複購買を防げません。

購買の承認権限は 1Approval ではなく kintone / Microsoft 365 側で決まります。二重管理にしないための切り分けです。

4. 監査ログを最初から入れる

固定資産と在庫は会計数値に直結するので、あとから足せません。資産計上・除却・在庫の手動調整・会計出力・権限変更・接続情報の変更を追記のみで残し、7年保存します。ログの閲覧自体も記録します。

5. 取り込みの冪等性

同じ注文を二度取り込んでも二重にならないこと。外部キー（注文番号・行番号）で upsert します。出荷通知も請求通知も同じです。キーはチャネル・文書種別・文書ID・行IDの4点で持ちます。文書種別を含めておかないと、次の「4文書型」が入った瞬間に注文と出荷通知が同じキー空間で衝突します。

6. 外部との入出力を4文書型に正規化する

EC・EDI・会計・将来のカード明細まで、外部とのやり取りを発注 / 注文確認 / 出荷通知 / 請求の4つの文書型に正規化し、接続先ごとの差はアダプタに閉じ込めます。この4つは Peppol のポストアワード文書（Order / Order Response / Despatch Advice / Invoice）と同じ切り方で、cXML もこの形に写せます。内部モデルの項目名とコード体系は EN16931 / JP PINT に合わせます。接続するかどうかとは無関係に、自前設計を回避するために採ります。根拠と具体は外部データ標準（Peppol / EN16931）の章にまとめました。

分類エンジン（機能②③④を一本化）

このレビューで最も大きな修正提案です。ボタンを3つに分けるのではなく、1つの分類エンジンと、3つのビューにしてください。

分けてはいけない理由は単純です。試薬は「消耗品」でもあり「期限管理」でもあり、高額な分析機器は「固定資産」であり「校正期限あり」です。排他のボタンにすると、どちらかに入れた瞬間にもう片方の管理が落ちます。

推奨する形は、明細1行に対して管理区分と期限管理の有無（フラグ）を持たせることです。

判定の順番は上から順に、当たったところで確定します。

  1. 品目マスタ照合（品番・JAN）— 登録済みなら勘定科目・管理区分・期限管理の有無まで決まる。最優先
  2. カテゴリ既定値 — マスタ未登録なら EC のカテゴリから推定
  3. 金額しきい値 — 税抜・1個あたり。テナント設定の10／20／30万円
  4. 例外ルール — 送料・役務・保守は金額に関係なく費用固定。セット品は按分
  5. 過去の手直しからの学習 — 人が直した結果を次回の既定値に昇格

判定には確信度を付け、低いものだけを未分類としてレビューキューに出します。これが画面上の「分類の確定」です。

② 固定資産化

しきい値を超えたものを候補として抽出し、人が確定します。不足していたのは逆方向の処理です。除却・売却・廃棄がないと、台帳が増える一方になります。

③ 消耗品

最大の設計論点は在庫が減る瞬間の定義でした。決定は QR 出庫です。安全在庫は初期は「平均消費量 × リードタイム」の単純な式で十分です。

自動購買申請は暴走防止が必須です。同一SKUで未完了の申請がある間は再起票しない、を入れてください。

④ 期限

期限は品目ではなくロットに付きます。同じ試薬でも入荷日が違えば期限が違います。取り出すときは期限の近いロットから（FEFO）。

購買時のアラートは、申請画面で同SKUの期限ロットを見せる形が最も効きます。買う前に気づかせることが重要で、買ったあとの通知では遅いです。

購買明細台帳と検収

機能① 購買明細台帳

方向は正しいです。不足は明細粒度・税情報・検収の3点と、アラートの判定ロジックでした。

追加すべき項目は、明細行ごとの税率区分・税抜金額・税額、検収ステータスと検収日・検収者、発注数量と受領数量の両方、ロット番号とシリアル番号、送料・手数料の按分です。

電帳法対応をスコープに入れたので、取引年月日・取引金額・取引先の3項目で検索でき、金額は範囲指定できることが要件です。

アラートはすべてルール設定画面でしきい値を持ちます。相場超過は過去12か月の中央値比、1.5倍以上で理由の記入を必須に。重複は同一品番・7日以内・全拠点横断。分割発注はしきい値直下が30日で3回。各アラートには状態（未対応／確認済み／問題なし）を持たせます。

CSV出力の設計

「会計ソフトを指定する」だけでは回りません。勘定奉行・PCA・freee・マネーフォワード・楽楽精算・バクラクの6製品に出すので、内部に1本の正規化した仕訳行テーブルを持ち、製品ごとはマッピングで出す形にしてください。製品ごとに出力処理を書くと、7製品目でデータ構造を触ることになります。

#### この内部カラムは自前設計しない

上の表は、ほぼそのまま EN16931（およびその日本版である JP PINT）の請求書セマンティックモデルです。税率区分・税抜金額・税額を行ごとに持ち、税率ごとの小計を文書単位で持ち、取引先に登録番号を添える——という構造は規格側で確定しているので、内部キーとカラムの意味は規格に合わせ、各社CSVへの変換だけを自分で書きます。詳細は外部データ標準の章。

#### 4つのマスタが要る

勘定科目マスタ（1Approvalの科目 → 各社のコード／名称）、税区分マスタ（EN16931 の税カテゴリを内部キーとし → 各社の税区分表記へ）、部門マスタ、取引先マスタ（法人番号を主キー、T番号は別項目、各社の取引先コードはマッピング）。これが接続設定画面の「項目マッピング」の中身です。単位コードの変換表も同じ場所に置きます。

#### つまずきやすい4点

税抜／税込の入力設定。奉行やPCAは会社ごとに税抜入力か税込入力かが決まっていて、そこに合わない金額を渡すと税額が二重になります。接続設定で保持してください。

インボイスの経過措置。非適格の取引先からの仕入は、2023年10月〜2026年9月が仕入税額相当額の80%控除、2026年10月〜2029年9月が50%控除、2029年10月以降は控除なしです。切り替わりは取引日で決まるので、控除率はテナント設定ではなく、適用期間を持った共通テーブルとして保持し、明細の取引年月日から自動で引きます。T番号の有無を明細に持っておくことが前提です（EN16931 でいう取引先の税登録番号にあたります）。

freee だけ思想が違う。仕訳ではなく「取引（収入／支出）」で入れる設計なので、借方・貸方を組むのではなく、勘定科目＋決済口座＋税区分で1行です。ここだけ変換ロジックが別になります。

再出力の扱い。出力済みフラグを持ち、同じバッチを二度出したら会計側で重複します。出力履歴と再出力を明示的に分けてください。

この形にしておくと、7製品目が来てもマッピング定義を1つ足すだけで済みます。出力単位（明細／伝票）、勘定科目と補助科目のマッピング、部門コードの変換も、すべてこのマッピング定義に含めます。

検収がすべての起点

当初の仕様には検収する画面がありませんでした。これが最大の欠落です。

flowchart LR A[発注済み] --> B[出荷通知] B --> C[検収（スマホ）] C --> D{数量が合うか} D -->|合う| E[分類の確定] D -->|合わない| F[差異の処理] E --> G[在庫・資産台帳へ] E --> H[会計へ出力]

入口は3つ用意します。送り状バーコード（ShipmentIdentifier）、今日の到着予定から選ぶ、注文番号の手入力。納品書のQRは前提にできません。

差異の処理

持つ数量は発注数・出荷数・受領数・未達数の4つで、差異には理由コードを付けます。これは Peppol の出荷通知（Despatch Advice）が持つ構造と同じで、下の表はその理由コードごとの処理規則にあたります。理由コードは自前で発明せず、標準の体系を内部キーにします（詳細は外部データ標準）。

記録するのは差異の数ではなく理由です。理由が決まれば、注文・在庫・請求・承認の扱いが自動で決まります。

理由注文在庫お金
分納開いたまま、残数が到着予定に残る来た分だけ請求も分かれて来る
欠品・打ち切り残数をクローズし発注数を減らす来た分だけベンダー側の請求が減額される
破損・誤品返品数は未受領扱い入れない貸方請求を待つ
過納返送か受け入れ受け入れるなら増える超過分は承認が要る
数え間違い変わらない変わらない変わらない

重要な判断が2つあります。受け取っていない数量は台帳に載らないので、除却は発生しません。そして減額は自社で直すのではなく、ベンダーの請求自体が減るのが正です。1Approval は3者照合（発注・検収・請求）で止める側に回ります。

許容差（数量±2%・金額±1,000円）の内側は理由を聞かずに通します。この値もルール設定で持ちます。

自動検収（みなし検収）

モノタロウの実態を確認した結果、先方は出荷ベース（出荷期日基準）で運用しています。検収払いを希望するのは大手製造業中心で、数としては多くないとのことでした。検収をしたい企業では、出荷から1日ずらして自動計上する仕組みや、配送リードタイム（北海道など＋1日）を考慮した運用をしています。

重要なのは、One Source Lite にも検収機能がないことです。つまり検収は EC 側では埋まらず、1Approval が持つ意味がある領域です。ただし現場に全件スキャンを要求すると定着しません。自動検収を既定にし、例外だけ手でやる形にします。

検収モードは品目区分ごとに3つ持ちます。

モード対象検収日根拠
自動検収消耗品、管理対象外、低額品出荷日 ＋ 拠点別リードタイム（営業日）出荷通知（ShipNoticeRequest）
手動検収IT機器、期限管理品、固定資産候補スキャンした日現場の記録
両方上記以外先に行われた方手動があれば手動を採用

IT機器と期限管理品は自動検収にしてはいけません。シリアル番号とロット・期限が取れなくなり、MDM突合と FEFO が成立しなくなるからです。固定資産候補も、現物を見ずに資産計上するのは避けます。

#### 自動検収のパラメータ

拠点ごとの配送リードタイム（本州＋1日、北海道・沖縄＋2日など）、営業日カレンダー（土日祝と年末年始）、自動検収の上限金額（超えたら手動）、対象カテゴリ、訂正の窓（既定7日）。すべてルール設定に持ちます。

#### 後から違ったと分かったとき

自動検収は「届いたはず」というみなしなので、事後訂正の経路が必須です。訂正の窓の内側なら、数量を直すと在庫に correction の動きが立ち、仕訳が未出力ならそのまま、出力済みなら赤伝票として次のバッチに乗ります。

みなし検収した明細には auto_received フラグと、根拠（出荷通知の日時・適用したリードタイム） を残します。監査で「誰が検収したのか」を聞かれたときに、人ではなくルールだと説明できる必要があるからです。

#### 計上基準との関係

自動検収にすると、実質の計上日は「出荷日＋リードタイム」になります。検収基準を採る企業にとってはこれが検収日の代用になるので、月次の締めをまたぐときの扱い（末日出荷は翌月計上になる）を設定で選べるようにしてください。出荷基準で良い企業は、リードタイムを 0 日にすれば出荷日計上になります。

現物管理（機能⑤〜⑧）

⑤ 個体管理

追加すべきは5点。状態の持ち方（在庫中・貸出中・修理中・除却済み）、現在位置と使用者の分離、所有区分（自社／リース／レンタル）、取得・事業供用日・耐用年数、そして購買明細への逆引きです。

⑥ 貸出・予約

最重要の抜けは予約の競合制御でした。同じ個体に重なる期間の予約を入れさせないこと。カレンダー表示にしたのはこのためです。

そのほか、返却予定日と延長の可否、引き渡し時の状態確認、校正期限が返却予定日をまたぐ個体は選べないこと、付属品のチェック。

⑦ 棚卸

「全てのQRを読みに行く」では回りません。プロジェクトとして管理します。対象範囲を決め、担当と期間を持ち、未スキャンが残る前提で差異の理由付けをする。差異の理由は紛失・所在違い・登録漏れ・破棄済みの4択。

複数担当者が同じ個体を読んだ場合は後勝ちではなく、最初のスキャンを採用します。

⑧ 点検・修理

当初の仕様は故障後の対応だけで、予防保全（定期点検・校正）が抜けていました。測定機器は校正が切れると使えません。期限切れの個体は貸出できなくなる、を仕様に入れます。

修理はお金がかかるので承認を通します。見積が取得価額の50%を超えたら買い替えを提案します。費用は原則修繕費、価値を高める改修は資本的支出として資産に乗せます。

人と外部台帳、承認基盤連携

⑨ メンバー管理

氏名・部署だけでは不十分です。権限マトリクスを先に埋めること、退職・異動で回収・引き継ぎタスクを自動起票すること、SSO とユーザー同期を入れること。3つ目は Phase-4 に分離しました。

⑩ 固定資産ソフト連携

CSV を出すだけでは不十分で、突合レポートが必要です。固定資産ソフトから資産一覧を取り込み、片方にしかないものをリスト化します。連携項目には事業供用日（取得日とは別。償却開始の基準）を忘れずに。

⑩-2 リース

アストロラボとの突合で唯一不足していた領域です。リース品は「現物はあるが自社資産ではない」ので、所有区分で分けます。

保持するのは、リース会社、契約番号、満了日、月額と総額、解約通知期限、中途解約違約金、残価。満了時は再リース・買取・返却の3分岐を、90日前に促します。

返却時に現物が見つからないと弁償が発生するので、リース品こそ棚卸対象に含めます。

会計面では、企業会計基準第34号により 2027年4月1日以後開始の事業年度から、オペレーティング・リースも含めて使用権資産とリース負債を計上します。これは追い風です。リース契約を漏れなく集める必要が生じるからです。

11 MDM 連携

実装上の論点はシリアル番号の取得経路だけです。出荷通知には含まれないので、検収時にスキャンして紐づけるのが現実解です。

12 SaaS ライセンス

SaaS は「個体」ではなく「契約」です。個体IDのモデルを流用せず、契約（Subscription）と席（Seat）という別エンティティにします。年間契約は更新時しか席数を減らせないので、解約通知期限から逆算して棚卸しを促します。

13 承認基盤連携

購買でやっていることを、貸出と入退社にも広げます。

貸出申請は kintone / M365 で行い、承認された瞬間に貸出予約が確定します。購買と同じ形です。承認前は仮押さえで、他の人の確定予約が優先します。

入退社承認をトリガに、支給セットの購買申請・ライセンス付与・回収 ToDo が自動で走ります。ToDo は通知ではなく状態を持つタスクとして扱います。これで「退職者のPCが戻ってこない」が止まります。

データモデルと状態遷移

中核は6つです。PurchaseLine（購買明細）、Item（品目マスタ）、AssetItem（個体）、StockBalance / StockMove（在庫）、Lot（ロットと期限）、Subscription / Seat（SaaS）。

在庫は StockBalance（現在高）＋ StockMove（動きの台帳） の二層を推奨します。差分だけで持つと棚卸のときに追えなくなり、現在高だけだと原因が分からなくなります。

外部データ標準（Peppol / EN16931）

外部とのデータのやり取りを、どこまで標準に寄せるかの方針です。「Peppol に接続する」と「Peppol のデータモデルを借りる」は別の話で、前者は今やる理由が薄く、後者は接続の有無と無関係に効きます。3層に分け、AとBを仕様に含め、Cは条件付きで先送りします。

層内容判断
A. セマンティクス層内部の正規化モデルの項目名・コード体系を EN16931 / JP PINT に合わせる採用。Wave 1（Phase-0）
B. 文書モデル層外部との入出力を 発注 / 注文確認 / 出荷通知 / 請求 の4文書に正規化し、接続先ごとの差をアダプタに閉じる採用。Wave 2（検収と同時）
C. ネットワーク接続Peppol のアクセスポイント契約、SMP 登録、JP PINT の検証先送り。着手条件のみ決める

AとBを採る理由は、標準に合わせるコストを払うためではなく、自前設計を回避するリターンのためです。税区分の内部キー、差異の理由コード、取引先の名寄せキー、単位の正規化——どれも自分で発明すると後から穴が出る箇所で、そのすべてに既存の答えがあります。

A. セマンティクス層（Wave 1）

やることはカラムの意味とコード体系を規格に寄せるだけです。UBL の XML を実装するわけではなく、DB はリレーショナルのまま、語彙だけ借ります。規格の任意項目を網羅する必要もありません。

持つもの準拠先それで何が決まるか
取引先の識別法人番号を主キー（Peppol 参加者識別スキーム 0188 の体系）。T番号は別項目名寄せが文字列の突合ではなくキーの照合になる。会計6製品で最も失敗するのが取引先名の表記揺れなので、ここが単独で一番効く
税区分EN16931 の税カテゴリ＋税率。経過措置の控除率は適用期間付きの共通テーブル各社の税区分コードへの変換表は変わらず必要だが、内部側の仕様が固定される。経過措置の切り替わり（2026年10月に80%→50%）が取引日から自動で決まる
税額の持ち方行ごとの税抜金額・税額に加え、税率ごとの小計を文書単位で持つ端数処理の責任分界が決まる。税額を自分で持つか相手に計算させるかの出し分けが、接続設定だけで済む

証憑の参照証憑番号・ファイルURL・種別電帳法の検索3キー（取引年月日・金額・取引先）が文書モデルから自動で埋まる

この層はWave 1 で入れます。あとから直すのが最も高い部分で、かつ Wave 1.5 の会計CSVがそのまま乗る先だからです。

B. 文書モデル層（Wave 2）

外部との入出力を4文書に正規化します。Peppol のポストアワード文書、cXML、社内の呼び名の対応は次のとおりです。

注文確認Order ResponseConfirmationRequest分納・欠品・打ち切りの通知

出荷通知が、そのまま検収の入力仕様になる

Peppol の Despatch Advice は、行ごとに発注数・出荷数・未達数・未達理由コードを持ちます。これは検収の章の差異処理の表（分納・欠品・破損・過納・数え間違い）と同じ構造です。つまり差異理由コードを自前で決める必要がありません。内部キーは標準の理由コード体系を採り、理由コードから「注文を開いたままにするか」「在庫に入れるか」「請求をどう扱うか」が決まる変換表を1枚持ちます。

さらに Despatch Advice はロット番号とシリアルの入れ物を持ちます。モノタロウ cXML にシリアルが無いのは cXML 側の制約なので、内部の出荷通知には最初から両方を持たせます。期限管理（FEFO）と MDM 突合の前提がここで揃います。

3者照合の定義

3者照合は発注・出荷通知・請求の3文書の照合と定義し直します。参照は発注番号＋行番号でたどり、許容差（数量±2%・金額±1,000円）の判定は文書型に依存しません。

アダプタの責務

Adapters::Ec::Registry の ec_kind ごとのアダプタは、外部フォーマット → 内部4文書の変換器です。cXML が1本目、Peppol のアクセスポイントを足す場合も、カード明細・立替精算・CSV取込も同じ口に差さります。残る論点にあった「チャネル拡張のためにデータ構造をどうするか」は、これで決着します。

C. Peppol ネットワークへの接続（先送り）

今やらない理由は4つです。

  • 国内の Peppol 流通は実質インボイスのみで、発注・出荷通知の流通はほぼ無い。繋いでも相手がいない
  • 主要な調達チャネル（モノタロウ、One Source Lite）が cXML で、Peppol に乗っていない
  • 受信側になるにはアクセスポイントの契約（または自前認定）が必要で、実費と運用責任が発生する
  • 資産・在庫・貸出・リース・SaaS（機能⑤〜⑫）は Peppol の範囲外で、仕様の過半には何も効かない

着手条件はどちらか一方を満たしたときです。①顧客の仕入先が JP PINT で請求書を送れるようになったとき——AとBが済んでいれば、アダプタ1本で3者照合の対象が広がります。②顧客の取引先が調達要件として Peppol 対応を求めたとき。

期待してはいけないことも書いておきます。Peppol にも在庫引当のセマンティクスはありません。LP の「申請時点で在庫を確保」の裏付けにはならないので、モノタロウへの確認は引き続き必要です。

モノタロウ接続

仕様書（MonotaRO cXML Specification v2.11）を取得して確定した内容です。それ以前に「取れない」と書いていた項目の多くが覆りました。

実装の現状

eichiii-inc/1approval で実装済みのEC接続は pikapaka（出張）のみです。モノタロウは未実装。ただし受け皿はできています。Adapters::Ec::Registry に ec_kind を追加する形で、アダプタを差し込めます。

このアダプタの責務を、ここで「外部フォーマット → 内部4文書（発注・注文確認・出荷通知・請求）への変換器」と定義し直します。モノタロウ cXML はその1本目です。台帳や検収の側は cXML を知らず、内部4文書だけを見ます。将来 Peppol のアクセスポイントを足す場合も、カード明細や立替精算を足す場合も、同じ口に差さります。

対応文書は7種

チェックイン（PunchOutSetupRequest）、カート戻し（PunchOutOrderMessage）、発注（OrderRequest）、注文確認（ConfirmationRequest）、商品検索（PunchOutItemSearchRequest）、出荷通知（ShipNoticeRequest）、請求通知（InvoiceDetailRequest）。

重要なのは後ろ2つです。納品タイミングと税額の内訳が取れます。出荷通知からは ShipControl 配下の CarrierIdentifier と ShipmentIdentifier（送り状番号）、請求通知からは TaxDetail の TaxableAmount と TaxAmount。これで検収の入口と3者照合が成立します。

取れないことが確定したもの

シリアル番号は含まれません。検収時のスキャンで補います。ただしこれはcXML の制約であって、文書モデルの制約ではありません。内部の出荷通知にはロット番号とシリアルの入れ物を最初から持たせておきます（Peppol の Despatch Advice は両方を定義しています）。将来シリアルを送れる仕入先が現れたとき、IT機器の手動検収をスキャンなしに緩められるかどうかが、ここで決まります。

先方の実運用（ヒアリング）

仕様書とは別に、運用の実態も確認しました。設計に直接効くので4点残しておきます。

  • モノタロウ側は出荷ベース（出荷期日基準）で運用している
  • 検収払い（検収基準）を希望するのは大手製造業中心で、数としては多くない
  • 検収をしたい企業は、1日ずらして自動計上する仕組み（検収漏れ防止の自動化）や、配送リードタイム（北海道など＋1日）を考慮した運用をしている
  • One Source Lite にも検収機能はない

これは両面です。検収が EC 側で埋まらない以上、1Approval が検収を持つ意味はある。一方で、市場は出荷ベースで回っているので、全件の現物検収を前提にすると運用が重すぎる。だから自動検収を既定にし、IT機器と期限管理品だけ手でやる形にします。

在庫確保の扱い（未解決）

cXML パンチアウトに在庫引当のセマンティクスはありません。オレンジコマースの資料でも「在庫引当ができれば予定納期を連携」と、出荷通知段階の話として書かれています。

LP の「申請時点で在庫を確保」という表現は、現状の仕様書だけでは裏付けられません。モノタロウに確認すべき最優先事項です。

代わりに仕様書で裏付けられるのは、カート内容と総額を確定させて承認に回せることと、発注後に ConfirmationRequest で注文の受付を確認できることです。

アストロラボとの突合

同社が掲げる備品管理クラウドの機能12項目のうち、11項目は今回の仕様でカバーできています。

カバー済みは、台帳管理、QRラベル、棚卸、貸出予約、在庫、期限、点検・修理、除却、拠点・ロケーション、権限、スマホ対応。

差分はリース管理のみでした。これは機能⑩-2 として仕様に追加済みです。

逆に、こちらにしかないものがあります。購買明細から台帳が埋まることです。アストロラボは台帳から始まるので、最初の登録を人がやります。こちらは検収が登録を兼ねるので、入力の負担が構造的に少ない。ここが競合との差分です。

UI 設計

他社3製品（アストロラボ・dxeco・ジョーシス）の公開情報を見たうえでの情報設計です。3社は中核に置くものが違うため、メニューの並びが根本から違います。

取るべきは3つ。タスクを並べるホーム（通知メールだけだと見られない）、人軸のビュー（誰が何を持っているか）、登録の負担を下げる工夫。

取らないものは2つ。発見系のUI（ブラウザ拡張でのSaaS検知など）と、台帳を中核に置く構成。1Approval の中核は台帳ではなく未処理の購買明細です。

メニューの群

購買（台帳・支出分析）、モノ（検収・備品・在庫・期限・貸出・棚卸・リース）、IT・SaaS、人（メンバー・入退社）、設定の5群。他社にないのが購買群を先頭に置いていることです。

検収はモノ群の先頭に置きます。受け取る行為は、買う行為ではなくモノが増える瞬間だからです。購買群は Phase-0 の台帳と分析だけになり、フェーズの境目とメニューの境目が一致します。

主要画面

ホーム（やること） は数字を並べるダッシュボードにしません。行動できるものだけを並べ、各行はクリックするとその場で片づく。

購買明細台帳 の列は WHO / WHAT / WHEN / WHERE / WHY の5軸を踏襲します。電帳法対応として取引年月日・金額（範囲）・取引先で検索できること。

個体詳細 は1画面に全部入れます。上部に状態バッジと現在位置・使用者、下に取得情報と履歴。リース品は満了までの残日数と解約通知期限を常時表示。

現場のモバイル

検収・出庫・貸出・棚卸は全てスマホで、片手で1分以内。PC画面の縮小版にはしません。オフライン前提です。倉庫や工場は電波が届かないことがあります。

画面をまたぐ共通ルール

状態は色だけで区別しない。色覚異常と屋外の視認性のため、必ず文字を添えます。

一覧画面の作法は、保存した絞り込みを持つこと、行から次の操作に飛べること、CSVはその場で落ちること。

通知は対象者を絞り、鍵を持たせる。全員に送ると誰も見なくなります。同じ対象への重複通知は1日1通にまとめます。

実装順序と、残る論点

機能番号順に作ると手戻りします。依存関係の順に並べ直してください。

Waveフェーズ内容理由
1Phase-0購買明細台帳、品目マスタ、拠点・権限、監査ログ、セマンティクス層（A）他の全てがこれに乗る。カラムの意味とコード体系はあとから直すのが最も高い
1.5Phase-0分類エンジン、ルール設定、支出分析、予算、会計・経費CSVここで発注も検収もせずに会計へ出せる状態になる
2Phase-1検収と差異の処理、承認＝発注（PunchOut）、文書モデル層（B）1Approval が書き込みを始める。出荷通知を扱う最初の場所なので、4文書型はここで実体になる
3Phase-1在庫、出庫（スマホ）、期限、拠点間の移動消耗品の運用が回り始める
4Phase-1個体管理、QRラベル、棚卸現物と紐づく
5Phase-1貸出・予約、点検・修理、除却、リース個体台帳があって初めて成立
6Phase-1承認基盤連携（13-1 貸出・13-2 入退社）貸出とメンバーが先に要る
7Phase-2固定資産ソフト連携、MDM、SaaS外部システム依存

Wave 1 と 1.5 が Phase-0 です。ここまでで「買った明細が全部集まって、支出が見えて、会計に出せる」が完結します。発注も検収もしないので、現物管理の負担（QR貼付・初期棚卸）が発生しません。導入の最初の山を越えやすい切り方です。

Wave 2 から Phase-1 で、1Approval が発注と検収を実行し、台帳に書き込みを始めます。

MVP は Wave 1 + 1.5（Phase-0） です。従来 Wave 2 までを MVP としていましたが、Phase-0 だけでも会計に出せる価値が完結するため、ここで一度切れます。承認＝発注は Phase-1 です。逆に、個体管理（Wave 4）を最初のリリースに入れないことを推奨します。QRの貼付と初期棚卸が重く、ここで止まる導入が多いからです。

残る論点

決定事項は埋まりました。残っていた2件のうち、チャネル拡張は文書モデル層（B）の採用で決着したので、残るのは1件です。

モノタロウの在庫引当。ShipmentIdentifier に実際に何が入るかと合わせて、先方に確認が必要です。LP の表現に直結します。

購買明細台帳のチャネル拡張（決着）。カード明細や立替精算をいつ入れるかは未定のままで構いませんが、データ構造は後からチャネルを足せる形にします。具体的には、取り込みのキーにチャネルと文書種別を含め（前提5）、外部との入出力を4文書型に正規化する（前提6）。画面を作らなくてもこの2つは Phase-0 で入れます。
